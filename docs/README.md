Architectural Blueprint and Requirements Specification for a High-Performance Open-Source Media Library Manager
Introduction and System Overview
The contemporary digital media consumption landscape demands uncompromised visual fidelity, instantaneous interface responsiveness, and robust cross-platform interoperability. Users expect their personal media libraries to perform with the same fluidity and visual excellence as enterprise-grade commercial streaming services. The objective of this comprehensive architectural report is to outline the exact technical specifications, open-source libraries, and infrastructural requirements necessary to construct a bespoke, open-source media library manager from the ground up.
This platform is specifically designed to ingest, organize, and stream expansive libraries comprising 3,000 to 10,000 massive video assets, including extensive episodic television series and high-bitrate cinematic files. The system architecture is mandated to natively support advanced modern file formats and codecs, including H.264 (AVC), HEVC/H.265, AV1, raw 1080p, and pure 4K configurations encompassing High Dynamic Range (HDR10, HDR10+, HLG) and complex Dolby Vision profiles.
To achieve maximum platform reach without the unsustainable overhead of duplicating codebases, the client architecture will target both Apple TV (tvOS) and Android TV utilizing specialized cross-platform JavaScript frameworks. The user interface is required to replicate the highly interactive, dynamic "Netflix-style" experience, complete with advanced spatial navigation and delayed hover-to-play trailer mechanics. Finally, the entire backend infrastructure will be containerized via Docker and packaged specifically for seamless deployment on Unraid servers through a specialized XML template, bypassing the need for initial user authentication systems to prioritize sheer performance and frictionless local network access.
Data Persistence and Metadata Architecture
At the foundational layer of the media manager is the backend engine, responsible for rapidly indexing the file system, extracting complex video metadata, managing relationships between television shows and episodes, and serving this normalized data to the front-end clients with near-zero latency. For a library containing up to 10,000 massive media items, the backend must be optimized for heavy read operations and rapid API responses that prevent the user interface from stalling during high-speed scrolling.
Relational Database Engine Selection
While enterprise web applications frequently default to distributed, client-server SQL databases like PostgreSQL or MySQL, the specific deployment target of a single-node Unraid Docker container alters the optimal architectural paradigm. For a dataset of approximately 10,000 video records, associated metadata, cast information, and trickplay image references, the data scale is well within the highly optimized capabilities of SQLite1.
Historically, SQLite has been viewed strictly as a prototyping tool or a mobile application storage mechanism. However, in modern architectures running on NVMe solid-state storage, it presents significant architectural advantages over traditional client-server databases. A PostgreSQL deployment requires a separate stateful daemon, inter-process communication (IPC) overhead, serialization and deserialization over local network sockets, and a substantially larger memory footprint2. In contrast, SQLite operates as a highly optimized, embedded, in-process C library.
The performance characteristics of SQLite can be dramatically enhanced by tuning it for modern hardware. Traditional SQLite configurations utilize a default 4KB page size, which was chosen in an era of spinning magnetic disks with 512-byte sectors2. Modern NVMe drives, however, possess massively parallel internal architectures consisting of multiple NAND dies organized into planes, accessed through independent channels, and managed by controllers with deep command queues. A 4KB read request exercises only a microscopic fraction of this parallelism. By expanding the SQLite page size to 64KB, the database aligns its read requests with the drive's internal geometry2. This larger page size reduces B-Tree depth—resulting in more keys per node and fewer hierarchical levels to traverse—while simultaneously saturating the NVMe drive's parallel channels and amortizing system call overhead2.
Furthermore, to handle the concurrent read requests generated by a TV client populating a massive grid of posters, SQLite must be configured with Write-Ahead Logging (WAL) mode3. WAL mode allows simultaneous readers alongside a single writer, entirely eliminating database locking contention during playback queries while the server is concurrently running a background metadata scrape.

Metadata Extraction and Dolby Vision Profiling
To handle modern file formats seamlessly, the ingestion engine must accurately probe files upon detection to determine their exact codec configurations. The industry-standard open-source tool for this operation is ffprobe, a component of the FFmpeg multimedia framework. The ingestion pipeline must execute asynchronous ffprobe processes to extract deeply nested video metadata without blocking the main application thread.
The extraction logic must differentiate between Main 10 profile HEVC and standard H.264, identify SMPTE ST 2084 (PQ) transfer characteristics for HDR, and critically, extract Dolby Vision specific metadata4. Dolby Vision is not a monolithic format; it exists across several profiles with distinct behaviors. The system must index whether a file is Dolby Vision Profile 5 (which uses a proprietary IPTPQc2 color space and lacks backward compatibility), Profile 7 (often found in 4K Blu-ray rips featuring a base HDR10 layer and a Dolby Vision enhancement layer), or Profile 8.1 (which provides a standard HDR10 fallback)4. Storing this exact profile data in the SQLite database is mandatory, as it directly dictates the downstream transcoding and hardware acceleration pipeline required for playback on legacy SDR displays.
Transcoding and Hardware Acceleration Engine
A paramount requirement of this architecture is the ability to transcode heavy video formats—such as pure 4K Dolby Vision or high-bitrate HEVC—on the fly for clients or network conditions that lack native direct-play capabilities. Relying on software decoding via the CPU for these modern formats will instantly saturate a host processor, leading to severe thermal throttling and unwatchable, stuttering video playback. Therefore, a robust hardware acceleration (HWA) pipeline must be engineered into the backend.
The Transcoder Core: Utilizing jellyfin-ffmpeg
Relying on the upstream, vanilla branch of FFmpeg is architecturally insufficient for a modern media server dealing with complex HDR and Dolby Vision tone-mapping edge cases. The optimal open-source library choice for the transcoding engine is jellyfin-ffmpeg, a specialized, heavily patched fork of FFmpeg designed explicitly for continuous media server workloads6.
The upstream FFmpeg project prioritizes broad format compatibility and often deprioritizes or delays merging hardware-specific edge-case fixes. In contrast, jellyfin-ffmpeg reduces real-world playback issues by integrating targeted fixes for hardware acceleration, HTTP Live Streaming (HLS) generation, and complex subtitle burn-in scenarios6. Furthermore, it includes the highly optimized dav1d decoder, which dramatically accelerates AV1 software decoding in environments where an AV1 hardware decoder is physically unavailable, bridging the gap for older host machines8.
Hardware Acceleration APIs and Capabilities
To achieve optimal performance on an Unraid host, the backend application must interface directly with the host machine's graphics processing unit (GPU) via Docker device mappings. The application must dynamically assemble FFmpeg execution commands, selecting the appropriate acceleration API based on the detected hardware:
1. Intel Quick Sync Video (QSV): Intel's integrated GPUs (iGPUs) and newer Arc discrete GPUs represent the industry standard for media server power efficiency and visual quality. QSV operates with exceptionally low power draws. For example, an Intel UHD 770 integrated graphics chip (found on 12th and 13th Generation processors) can simultaneously transcode 4 to 7 standard 4K streams with a minimal power overhead of 6 to 10 watts. Upgrading to an Intel Arc A310 or A380 discrete GPU dramatically expands this capacity to 8 to 12 simultaneous 4K streams, while adding robust hardware encoding and decoding for the highly efficient AV1 codec7.
2. NVIDIA NVENC/NVDEC: For host systems utilizing NVIDIA discrete GPUs (Pascal architecture or newer), NVENC provides massive parallel transcoding throughput. While consumer-grade NVIDIA cards previously featured artificial, driver-level stream limits, modern drivers or community-developed patches allow for unbounded stream counts. An NVIDIA RTX 4060, for instance, is capable of handling 8 to 12 simultaneous 4K streams and also includes native AV1 encoding capabilities, making it ideal for high-density streaming environments9.
3. AMD Advanced Media Framework (AMF): Supported via the Video Acceleration API (VA-API) on Linux host systems, AMD GPUs (GCN architecture and newer) can be utilized for hardware acceleration. However, architectural consensus suggests that AMD encoders historically lag slightly behind Intel QSV and NVIDIA NVENC in raw visual quality at lower bitrates, making them a tertiary choice for media server deployments7.
The application logic must be intelligent enough to query the host's capabilities. It should avoid attempting hardware decoding for specific unsupported formats. For example, the hardware decoding of H.264 / AVC 10-bit (High 10 profile) video is universally unsupported by Intel, NVIDIA, and AMD GPUs; attempting to pass this to the hardware pipeline will result in instant playback failure. The system must programmatically fallback to software decoding when this specific profile is detected during the SQLite database query7.
High Dynamic Range and Dolby Vision Tone Mapping
When a user attempts to play a 4K HDR10 or Dolby Vision file on an Apple TV or Android TV connected to a legacy Standard Dynamic Range (SDR) television, the server cannot simply strip the metadata; it must perform mathematical tone mapping. Without hardware acceleration, computing the complex color space transformation from BT.2020/SMPTE2084 to BT.709/SDR requires immense vector processing power, frequently overwhelming even high-end enterprise CPUs and resulting in single-digit framerates8.
The architectural implementation must leverage hardware-accelerated tone mapping pipelines explicitly:
* Intel VPP (Video Post Processing): This is the highly recommended mechanism for standard HDR10 to SDR tone mapping on Intel hardware. VPP provides exceptional transformation speed with minimal latency overhead, utilizing the fixed-function execution units on the Intel silicon10.
* OpenCL and CUDA Integration: Standard VPP is insufficient for processing Dolby Vision. As previously noted, Dolby Vision Profile 5 operates in a proprietary IPTPQc2 color space. Standard HDR tone mapping filters applied to Profile 5 media will output heavily distorted, severely purple and green tinted video. jellyfin-ffmpeg supports OpenCL computing pipelines (for Intel and AMD hardware) and CUDA pipelines (for NVIDIA hardware) capable of mathematically translating Dolby Vision Profile 5 and Profile 8 down to standard SDR7.
The backend application logic must dynamically construct the FFmpeg command line string based on the exact profile metadata stored in SQLite. If a Dolby Vision file is detected alongside an Intel GPU, the system must chain the appropriate init_hw_device opencl commands to initialize the OpenCL runtime, utilize it for the intensive tone mapping phase, and seamlessly hand the processed frames back to the QSV pipeline for final H.264 encoding12.
This operation is heavily bound by memory bandwidth. When utilizing integrated GPUs for complex tone mapping, the iGPU leverages system RAM as its video memory pool. The architecture heavily relies on the host system utilizing dual-channel memory configurations, which effectively doubles the video memory bandwidth and prevents the OpenCL tone-mapping algorithms from starving for data7.
Client Application Architecture: Apple TV and Android TV Integration
Developing entirely separate, native applications for Apple TV (using Swift and Objective-C) and Android TV (using Kotlin and Java) introduces an unsustainable engineering burden, requiring dual codebases, duplicated bug fixing, and bifurcated feature parity for a unified open-source project. Conversely, attempting to utilize standard web wrappers (such as basic WebViews) yields unacceptable, sluggish performance on underpowered smart TV silicon.
Framework Selection: react-native-tvos
The optimal technological solution to achieve near-native performance while maintaining a single, unified codebase is React Native, specifically the community-maintained react-native-tvos fork. This specialized framework allows developers to author application logic in TypeScript and JSX, which the framework then compiles down into native UI components on both tvOS and Android TV15.
Unlike the core Meta React Native repository, which prioritizes mobile touchscreens, react-native-tvos contains deep, platform-specific patches tailored for television interfaces. These include intricate handling for directional pad (D-Pad) inputs, overrides for physical TV remote menu buttons, and hooks into the native focus-based navigation engines of both operating systems15. The development workflow can be further streamlined by utilizing the Expo ecosystem. Beginning with Expo SDK 54, the platform provides extensive, first-class support for TV builds via its Continuous Native Generation (CNG) model, completely abstracting the complexities of managing native Xcode and Android Studio project files18. By utilizing the template-tv community CLI boilerplate, the project immediately gains a scaffold optimized specifically for 10-foot user interfaces15.
Spatial Navigation and Focus Management Engineering
A television interface introduces a fundamentally different interaction paradigm compared to mobile development. A user does not utilize a mouse pointer or a touchscreen; user interaction relies entirely on moving an active focus state across a two-dimensional grid using a physical remote control. Managing this focus state—especially in complex grids of asymmetrical movie posters, side navigation drawers, and horizontal carousels—is historically the most challenging aspect of TV application engineering.
Standard React Native Touchable and Pressable components attempt automatic focus mapping, calculating the nearest neighbor when a user presses a directional button. However, this native heuristic frequently fails, particularly on Apple TV, when UI elements are not perfectly aligned along a rigid X or Y axis17. This leads to the focus state becoming "trapped" or jumping unpredictably to the wrong visual element, destroying the user experience.
To resolve this and ensure a flawless, deterministic user experience, the client architecture must implement a dedicated spatial navigation library. The highly recommended dependency for this task is react-tv-space-navigation19. This library abstracts the complexity of spatial routing, allowing the developer to explicitly define focusable nodes, directional boundaries, and logical groups.
Implementation requires engineering several specific spatial paradigms:
* Focus Traps: When a user opens a modal dialogue or a side-drawer menu, the spatial navigation library must trap the focus within that component, preventing the D-pad from accidentally highlighting background elements that are partially obscured.
* Directional Overrides: The UI must support explicit behavioral definitions. For example, explicitly defining that pressing "Down" on the hero banner automatically transitions the focus to the first item in the "Continue Watching" carousel, regardless of the exact geometric alignment of the two components.
* TVFocusGuideView Implementation: Specifically for Apple TV compatibility, the application must utilize the TVFocusGuideView component. This component acts as an invisible bridge, utilizing Apple's native UIFocusGuide API to manually map focus paths across empty spaces or asymmetrical layouts, ensuring that the tvOS focus engine behaves as the designer intended17.
Video Playback and Overlay Integration
The core interactive element of the application is the video player itself. For robust, cross-platform media playback within the React Native ecosystem, react-native-video serves as the foundational dependency, providing deep hooks into the underlying native media players (AVPlayer on Apple TV and ExoPlayer on Android TV)17.
However, architecting custom user interface controls (Play, Pause, Seek, Audio Track Selection) on top of a playing video introduces severe spatial navigation conflicts, particularly on Android TV23. If the custom video controls are placed in a standard React Native modal or an absolutely positioned wrapper over the video view, the native Android TV focus engine often struggles to route D-pad events correctly, sometimes losing focus entirely or causing immense render lag due to state thrashing23.
To engineer around this limitation, the client must abandon standard spatial navigation for the video player overlay. Instead, it must utilize the low-level useTVEventHandler hook provided by react-native-tvos23. By globally intercepting raw remote control hardware events (e.g., eventType: 'select', eventType: 'right'), the application can programmatically trigger video state changes and display custom overlay UI without relying on the native focus engine attempting to highlight invisible, overlapping UI elements.
For Apple TV, the architecture can optionally fallback to the native tvOS AVPlayer view controls. While the Bitmovin SDK and standard native players do not automatically map custom metadata (like dynamic titles and descriptions) into the native UI overlay without custom wrappers, leveraging the native player provides a premium, Apple-certified scrubbing and playback experience that users are intimately familiar with19.
Advanced User Interface Engineering: The Netflix-Style Hover Experience
A defining hallmark of modern, premium media applications is the highly dynamic interface, most notably the ability to navigate over a media poster and, after a brief, intentional delay, seamlessly transition that poster into a playing video trailer or trickplay preview. Executing this flawlessly requires precise timing and resource management.
Deterministic State Management via Finite State Machines
Implementing the Netflix-style hover preview is historically fraught with asynchronous race conditions. A naive implementation using standard React setTimeout hooks will inevitably result in videos attempting to play after the user has already scrolled away, or multiple hidden videos playing audio simultaneously as their timeouts resolve concurrently.
To guarantee absolute interface stability, this specific interaction must be governed by a strict finite state machine, optimally implemented using the xstate library25. The state machine deterministically controls every phase of the interaction lifecycle:
1. Awaiting Image Load: The UI component remains locked in an awaitingBackgroundImageLoad state. It is critical that no video logic executes until the underlying high-resolution poster image is fully downloaded, cached, and rendered. Attempting to load a video before the poster resolves results in a jarring visual pop and a degraded user experience25.
2. Idle and Trigger: Upon successful image load (REPORT_IMAGE_LOADED), the state transitions to idle. When the user navigates focus to the poster (via a MOUSE_OVER or D-pad focus event), the machine transitions to a nested waiting state25.
3. The Two-Second Gate: The state machine enters showingVideo.loadingVideoSrc.cannotMoveOn and pauses execution for exactly two seconds. This intentional gate is critical; it prevents the application from aggressively flooding the local network with video load requests and freezing the UI thread as the user rapidly scrolls past dozens of items to find what they want25.
4. Execution and Immediate Teardown: Once the two-second timer expires, the machine dispatches a REPORT_VIDEO_LOADED event, mounting the video component and initiating silent playback. Crucially, if the user moves focus away (MOUSE_OUT) at any microsecond during the two-second gate or during active playback, the state machine instantly aborts the network request, forcefully unmounts the video component, and returns safely to idle, completely eliminating the possibility of orphaned playback threads25.
Asynchronous Trickplay and Sprite Generation
For the hover preview to load instantaneously upon the conclusion of the two-second gate, the backend architecture cannot rely on live-transcoding the massive 4K source file just to display a 15-second loop. The latency of spinning up the FFmpeg process and buffering the transcode would completely ruin the seamless illusion. Instead, the backend must pre-generate optimized preview assets.
A dedicated background process—architecturally analogous to the logic found in the community tool Media Preview Generator—must be engineered to asynchronously scan the library during off-peak hours26. This worker process will:
1. Extract 10 to 15-second clip segments from the heavy source files.
2. Utilize FFmpeg hardware acceleration to aggressively downscale the clips to 720p, compress them using highly compatible H.264 encoding, and strip the audio tracks entirely to ensure silent UI previews.
3. Generate trickplay sprites (either Roku-style BIF files or tiled JPG matrices) to enable smooth visual scrubbing on the client's timeline26.
By offloading all preview generation to an asynchronous background worker and writing the lightweight assets directly alongside the media or into the application's config folder, the primary GPU resources remain entirely free for user-requested, full-length streaming. Meanwhile, the React Native client enjoys sub-second loading times for hover previews without taxing the server CPU26.
Deployment Infrastructure: Docker and Unraid Integration
The final core requirement dictates that the media server must be entirely containerized in Docker, pushed to a public GitHub repository, and inherently compatible with Unraid. Unraid relies on a proprietary Community Applications (CA) plugin ecosystem that parses specific XML templates hosted on GitHub to automatically generate Docker run commands and graphical configuration forms for end-users27.
Containerization Strategy and Image Composition
The application must be structured using a multi-stage Dockerfile to maintain a minimal attack surface and footprint:
1. Build Stage: Compiles the backend Go or Rust binary and bundles any required static assets.
2. Runtime Stage: Utilizes a minimal base operating system image. While Alpine Linux is popular for size, a Debian-based image (e.g., Debian Bullseye or Bookworm) is strongly recommended for a media server due to vastly superior compatibility with proprietary GPU drivers and FFmpeg dependencies.
3. Dependency Injection: The runtime image must explicitly pull and install the jellyfin-ffmpeg binaries. Furthermore, it must install the critical user-mode hardware acceleration drivers, including intel-media-va-driver-non-free and intel-compute-runtime for Intel QSV/OpenCL, and mesa-va-drivers for AMD VA-API10. NVIDIA support is dynamically injected by the host machine utilizing the NVIDIA container runtime.

By strictly defining these hardware parameters directly in the XML schema, an Unraid user can simply click "Install," select their media folders, and instantly deploy a fully hardware-accelerated media server.
Synthesis and Conclusion
Constructing an open-source media library manager capable of effortlessly organizing massive libraries and decoding modern, high-fidelity video codecs is an intricate orchestration of database optimization, hardware-accelerated stream manipulation, and specialized interface engineering. By utilizing SQLite configured with 64KB pages and Write-Ahead Logging, the architecture achieves the microsecond-level metadata retrieval necessary for fluid interface rendering, completely avoiding the overhead of client-server databases like PostgreSQL. Coupling this robust backend with the highly optimized jellyfin-ffmpeg pipeline guarantees the server can process complex mathematical transformations—such as Dolby Vision IPTPQc2 to SDR tone mapping via OpenCL—while keeping CPU utilization nominal and leveraging the dedicated silicon of Intel, NVIDIA, and AMD processors.
On the client front, abandoning fragmented native development in favor of react-native-tvos alongside the react-tv-space-navigation library ensures that the application can be deployed across the dominant television ecosystems from a single, unified TypeScript codebase. The implementation of strict XState finite state machines and asynchronous trickplay sprite generation guarantees that the premium, Netflix-style interface dynamics execute flawlessly without triggering network race conditions or starving the host GPU. Finally, encapsulating this entire architecture within a properly structured, hardware-aware Unraid CA XML Docker template fulfills the deployment requirements, resulting in a highly performant, easily distributable, and profoundly capable home media ecosystem.
